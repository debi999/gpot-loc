## 1. 重设计的动因

### 1.1 现状（v3.29 实证）

旧版主程序（v3.29，`StarmakerTranslator.py`）5240 行全部 UI 代码集中在 `_build_ui()`（2248–2522 行）里**平铺**，
产生了 **13 个平级操作入口**：

| 区域 | 按钮 |
|---|---|
| 顶部应用栏 | ⚙设置 / 保存 / 翻译▾ / 提取 / 识别引擎 / 注入工具 / 应用到游戏 |
| 中部工具条 | 导入 CSV / 导出 CSV / 查找替换 / 清理重复 / 重试失败 / 还原原文 |

三个具体问题：

1. **顺序是反的。** 正确的业务顺序是「选目录 → 识别引擎 → 提取 → 翻译 → 保存 → 应用」，
   但顶栏从左到右的实际排列是 `保存 → 翻译 → 提取 → 识别引擎`。第 4 步排在第 2、3 步前面。
2. **没有状态。** 用户做完一步后，界面上看不出做到哪了、还差什么。
3. **阶段错位。** `注入工具` 本来是跟着**引擎**走的一次性准备动作，
   却跟「识别引擎」并排挂在顶栏 —— 视觉上像是同类按钮，实际一个在第 2 步一个在第 5 步。

一句话：**现有界面是「能力清单」，不是「任务流水线」。**

### 1.2 目标

把 13 个入口按业务流程归位到 7 个步骤里，让用户**任何时候都知道自己在哪、下一步做什么、这一步做完了会怎样**。

## 2. 业务流程定义

### 2.1 老板给定的原始流程 vs 建议流程

老板原始 5 步：①选路径 → ②识别引擎 → ③提取 → ④翻译 → ⑤保存并注入。

建议调整为 **7 步**，两处调整、两处补充：

| # | 步骤 | 调整 | 理由 |
|---|---|---|---|
| 0 | 配置翻译服务 | **新增** | 原来藏在 ⚙设置里。不配 API 直接点翻译必然失败，失败却出现在第 4 步，用户会误判成自己操作错了 |
| 1 | 选择游戏目录 | 保留 | — |
| 2 | 识别引擎 + 部署注入工具 | **前置吸收** | 工具部署由引擎决定，不是「保存之后」才决定。且是一次性动作，跟每次都要点的「应用」性质不同 |
| 3 | 提取待翻译文本 | 保留 | — |
| 4 | 翻译与人工校对 | 保留 + 强调校对 | galgame 的口吻/称谓/双关，机器翻错比没翻更伤 |
| 5 | 保存并应用到游戏 | 保留 | — |
| 6 | 启动验证 | **新增** | 旧版点完「应用」没有下文，用户不知道生效没有 |

### 2.2 每步产出物与执行频率

| # | 步骤 | 产出物 | 频率 |
|---|---|---|---|
| 0 | 配置翻译服务 | 可用后端 + 模型列表 | 一次性（换 Key 时重配） |
| 1 | 选择游戏目录 | 根目录 + 游戏名片 | 一次性 |
| 2 | 识别引擎 + 部署工具 | 管线方案 + 工具就位 | 一次性（换游戏重来） |
| 3 | 提取待翻译文本 | 原文条目入库 | 游戏更新后 |
| 4 | 翻译与人工校对 | 译文（本地草稿） | 每轮迭代 |
| 5 | 保存并应用 | 游戏能读到的译文 | 每轮迭代 |
| 6 | 启动验证 | 确认生效，可回滚 | 每次应用后 |

> **这个频率区分很重要**：第 0~2 步做完一次就再也不用管。
> 日常改一句台词，只是「点 4 → 改 → 点 5 → 重启游戏」三下。

## 3. 功能需求（FR-35 ~ FR-49）

### 3.1 流水线导航

**FR-35 流水线导航轨**（新增）
- 左侧 272px 固定导航轨，自上而下展示 7 个步骤。
- 每项显示：序号状态标记 + 步骤名 + **动态副标题**（该步的实际结果，如 `Unity (Mono) · 3 个已就位`、`已译 9,102 / 14,679`）。
- 副标题必须在真正跑完该步后才有值 —— **没跑过的步骤副标题写「待执行」，不许编造**。
- 顶部显示当前游戏名片（图标 + 名称 + 路径缩写），不在标题栏显示（避免跟窗口按钮挤）。

**FR-36 柔性导航规则**（新增，**老板已拍板**）
- **可回跳**：任意已完成的步骤可点击回跳，回跳后允许修改并重新执行。
- **不可跳前**：未解锁的步骤不可点击（disabled），必须靠当前步的主按钮推进。
- 回跳到已完成的步骤时，**已完成的下游步骤保持完成态**，不因回退而清零
  —— 例如回第 2 步换了引擎，第 3 步之前提取的文本仍在，只是会被提示「当前引擎与提取时不一致，建议重跑第 3 步」。
- 提供「完成本步」快捷按钮，等价点击本步主按钮。

**FR-37 步骤状态持久化**（新增）
- 当前所在步骤 + 各步完成状态写入 `config.ini`（键前缀 `flow.`）。
- 下次打开应用回到上次所在的步骤，**默认从第 4 步进入**（日常改词的高频入口），而不是每次从头开始。

### 3.2 第 0 步 · 配置翻译服务

**FR-38 翻译服务前置配置**（重构自 FR-7 / FR-8 / FR-9 / FR-11 / FR-12）
- 首次启动**直接进入本步**（配合 FR-37 的持久化，配好过就不再出现）。
- 8 个提供方以卡片单选呈现，卡片上直接写清特点（免费/离线/需 Key/质量/费用）。
- 选中后展开该后端专属参数区（Base URL / Key / Model）。
- 底部常驻「测试连接」，结果以 InfoBar 呈现：**成功显示实测延迟，失败显示具体原因**（超时 / 401 / 模型不存在 / 端口没开）。
- 「保存并继续」在完成连接测试前为 disabled 态，鼠标悬停提示「先做一次连接测试」。

### 3.3 第 1 步 · 选择游戏目录

**FR-39 游戏目录选择**（重构自 FR-1 / FR-25）
- 路径输入框可编辑、可粘贴、回车跳转、双击弹出选择器（保留 v3.21.1 修好的手感，**不许退回 readonly 吞点击**）。
- **最近使用列表**：显示游戏名 + 路径 + **已积累译文条数** + 上次打开时间。
  条数来自扫描现有表，不为 0 时打「已配置」徽章。
- 目标目录已存在译文时，用 InfoBar 明确告知「已有 N 条历史译文，本次操作只做增量，不会覆盖」。
- 底部主按钮：「继续 · 识别引擎 →」。

### 3.4 第 2 步 · 识别引擎与部署注入工具

**FR-40 引擎识别与管线说明**（重构自 FR-26 / FR-38part）
- 识别结果大卡：引擎名 + 置信度 + **硬证据 chip 列表**（文件名/chip 名，不超过 5 个）。
- 置信度 ≥ 0.7 打「确定性高」徽章；0.4~0.7 打「需确认」，并默认展开「手动指定 ▾」。
- **管线说明三元组**（本 FR 的核心新增内容）：

  | 字段 | 取自 | 示例 |
  |---|---|---|
  | 文本从哪来 | 引擎提取策略 | 资源字节流提取 |
  | 译文写到哪 | `kit_catalog.get_sink()` 的 `file_tpl` | 词典 txt（BepInEx） |
  | 怎么才生效 | `kit_catalog.sink_apply()` 的 `need` / `hint` | 运行时替换 · 不改游戏 |

  这三句话把「后面会发生什么」在动手之前就说清楚，避免做完才发现白干。

**FR-41 注入工具部署前移**（自 FR 无关原第 5 步抽出）
- 工具清单表：工具 / 版本 / 大小 / **校验状态** / 就位状态。
- 校验状态必须区分 `已验证`（本机实拉并算过 sha256）与 `仅查过 API`，
  **沿用 `kit_catalog.verified` 字段原值，不许统一显示成已验证**。
- 部署来源优先级：I 盘 `toolcache/` 缓存 → ghfast 镜像下载 → 失败则提示手动。
- 主按钮文案随状态变化：「下载并部署（34 MB）」/「重新校验」/「全部已就位」。
- 提供「跳过，我手动装」，但跳过时在第 5 步顶部挂一条常驻提示。

### 3.5 第 3 步 · 提取待翻译文本

**FR-42 提取与护栏可视化**（重构自 FR-4 / FR-5 / FR-31 / FR-32）
- **扫描选项**：增量合并（默认）/ 重建 / 仅标签模式。三种必须写清代价
  （「重建」写 丢弃现表；「仅标签」写 慢 3 倍但长对话命中更好）。
- **护栏开关**：截断残片过滤、污染词条过滤、排除 resS/.resource。
  每个开关的**辅助文字写实测拦截率**（`上一轮拦掉 8,045 条（35.4%），0 误伤`），而不是描述词。
- 结果四宫格：本轮新增 / 已存在跳过 / 护栏拦截 / 在表总数。
- **已知缺口必须明说**：约 1,000 条长段对话拿不到（类型树被剥离），需 IL 级 hook，不在本期范围。
  不许把这 1,000 条藏起来当不存在。

### 3.6 第 4 步 · 翻译与人工校对

**FR-43 翻译主工作区**（重构自 FR-14 / FR-15 / FR-16 / FR-17 / FR-18 / FR-19 / FR-20 / FR-21 / FR-28 / FR-29 / FR-33）
- 四宫格指标：总条目 / 已翻译 / 未翻译 / 失败。
- 批量卡：进度条 + 并发设置 + **预计剩余时间**（按实测速度算，不给空白承诺）。
- **唯一主按钮**「翻译未译条目 ▾」，下拉四项：仅未翻译 / 当前筛选 / 全部 / 仅重试失败。
- 表格与现阶段能力持平：搜索、筛选（全部/未翻译/英文残留/已翻译）、排序、分页、双击内联编辑、
  右键行菜单、导入导出 CSV、查找替换、清理重复。
- **双击内联编辑必须真实落盘**（2026-10-10 老板实测补规）：双击译文格 → 输入框，
  Enter 或失焦保存、Esc 取消；保存走 `/api/row/edit` 立即原子写盘（含 `.bak` 轮转），
  并自动重判状态（清空译文回「未翻译」）；换行以 `\n` 转义落盘。
- **分页必须是真分页**（2026-10-10 老板实测补规）：页码条（« ‹ n/m › »）+
  **每页条数选择**（50/100/200/500）；后端 `/api/rows` 支持 `offset` 并返回
  `matched`（筛选命中数）与 `total`（全表条数）；筛选后翻页越过末页自动收回；
  序号跟随全表位置，不随页重置。
- **承诺小字**：主按钮下方一行「已译文不会被覆盖」。**禁止扩写成长句**
  （原写 26 字，老板 2026-10-09 指出密度过大，压到 9 字）。
- 失败条目单独计数并提供「仅重试失败」入口（现在的 `重试失败` 按钮升级为此常驻入口）。

### 3.7 第 5 步 · 保存并应用到游戏（**按引擎分流**）

**FR-44 按引擎自动变脸**（重构自 FR-21 / FR-27 / v3.29 的 apply/restore）

本步内容完全由 `kit_catalog.sink_apply(engine)` 的返回值驱动，**不做通用版**：

| 情形 | 判定 | 主按钮 | 伴随控件 | 改动范围 |
|---|---|---|---|---|
| A 运行时替换 | `need=False`（Unity 双版本、Ren'Py） | 「保存并写入词典」 | 隐藏「应用到游戏」「还原原文」 | 词典文件 + `config.ini`，**不动游戏本体** |
| B 必须回写 | `need=True` 且 `kind='rpgmaker'` | 「备份原文并回写游戏」 | 显示「还原原文」（危险色） | `www/data/*.json` + 自动备份 |
| C 无自动方案 | `need=True` 且 `kind=None` | 「导出 CSV」 | 显示缺失原因清单 + 通用钩子建议 | 仅本地草稿 |

- A 情形必须显式告知「游戏本体一个字节都不动」。
- B 情形在按下前必须以 InfoBar 警示「会改真实游戏文件，执行前自动备份」，
  并列出**字段白名单**（可翻）与**黑名单**（`characterName`/`faceName`/`battlerName`/`switches`/`variables`/JS 脚本 355·655/注释 108/`note`，翻了会崩图或插件失效）。
- C 情形（2026-10-10 老板拍板改版）：引擎选择器第三项文案为 **「Coming soon」**
  （原「无方案」）。选中后本步页面**只显示居中的「敬请期待」一行**，
  不渲染任何其它卡片（不再显示缺失原因清单 / 导出 CSV 等）。
- 写入前统一做 `TranslationStore.save()` 原子写 + `.bak` 三代轮转（沿用 FR-27）。

### 3.8 第 6 步 · 启动验证

**FR-45 应用结果闭环**（新增）
- **写入结果自检三项**：目标文件存在 / 条目数匹配期望 / 格式合法（无孤立等号、无重复键）。
  每项显示「通过 / 失败」，失败时给出可操作的下一步，而不是一句报错。
- 引擎专属提示：Unity 提示「需重启游戏才加载新词典，已在跑的先退干净」；
  RPG Maker 提示「立绘丢失就点还原原文回滚」。
- 操作区：「启动游戏验证」/「打开译文目录」/「还原到原文（危险色）」。
- **「启动游戏验证」与「打开译文目录」必须为真实动作**（2026-10-10 老板实测补规）：
  启动 = 后端在游戏根目录排除 CrashHandler/Unity/Setup 等干扰 exe 后取主 exe
  （`_find_game_exe`，Starmaker 实测命中 `Starmaker Story.exe`），
  以独立进程启动游戏（`os.startfile`）；打开译文目录 = 资源管理器定位译文落点。
- 「还原到原文」只在 B 情形显示（FR-44 已规定）。

### 3.9 全局

**FR-46 单主按钮原则**（新增）
- 每页至多一个主按钮（实心强调色），文案描述**本步的具体动作**
  （「翻译未译条目」「备份原文并回写游戏」），禁止出现泛化的「保存」「确定」。
- 其余操作一律次要态（描边按钮）或幽灵态（无边框）。
- 主按钮禁用时必须带 tooltip 说明禁用原因。

**FR-47 全局状态条**（重构自 FR-24 区）
- 左：当前操作的一句话**结果**（写「词典已写入 1,424,251 B」），任务结束后不残留「正在写入…」这类进行时态。
- 右：细条进度 + 百分比。空闲时整条淡出，不占视觉重量。

**FR-48 保存步骤锁定当前游戏管线**（2026-10-09 老板补规；2026-10-10 增补两细则）
- 第 5 步（保存并应用）的引擎选择器**默认锁定**到「第 2 步识别出的引擎」；选择器仅用于预览其它管线的落地形态。
- 当用户选择了**非当前游戏引擎**时，「保存并写入」按钮**禁用**，并出现警告条说明原因与解锁方式（点回当前引擎）。
- **细则 1（2026-10-10）**：管线徽章字母跟随**当前所选**管线（预览 RPG Maker 显示「R」、Coming soon 显示「C」），不恒为识别结果的字母。
- **细则 2（2026-10-10）**：选择非当前引擎时，「还原原文」按钮一并隐藏——预览形态下不允许出现任何写入/回滚动作入口。
- 后端 `/api/sink/apply` 二次校验：请求引擎 ≠ 当前游戏引擎时返回 `400 engine_mismatch`，前端即便绕过也写不进去。
- 理由：防止把 A 引擎的写入逻辑（如 RPG Maker 回写）套到 B 引擎游戏上导致数据损坏。

**FR-49 翻译为可选项，不卡保存**（2026-10-09 老板补规）
- 第 3 步（提取）完成后，第 4 步（翻译）与第 5 步（保存并应用）**同时解锁**；翻译不再是抵达保存的硬门槛。
- 内核 `_NEXT[3] = 5`：提取直接解锁到第 5 步。未翻译的条目仍可保存，已翻译的条目照常落盘。
- 理由：老条目已译、或用户只想先验证提取/写入链路时，不必强制跑完翻译。

### 3.10 窗口壳与交付体验（2026-10-10 老板实测反馈增补）

**FR-50 无边框窗口与无黑窗启动**（新增）
- **无边框**：移除原生标题栏；顶部栏左侧为品牌区，其后挂一条弹性拖拽带；
  最小化 / 最大化（还原）/ 关闭三键整合在顶栏右端（关闭键悬停红）。
  浏览器运行（无桥）时三键自动隐藏。
- **无黑窗**：交付形态下**不得出现任何控制台窗口**。启动链为
  bat（pythonw / start /min）→ `main.py`；GUI 模式下若进程自带控制台
  （真 pythonw 缺失、拦截器 shim 派生等场景），必须在导入重模块前
  以 `CREATE_NO_WINDOW` 无窗重启自身并退出父进程（`GPOT_NOWIN=1` 防循环）。
  `--no-gui` / `--open-browser` 调试模式保留控制台。
- 已知取舍：无边框暂无边缘拖拽缩放（pywebview 未内建），后续可用 Win32 消息补。

**FR-51 版本感知与版本常显**（新增）
- 后端以 `APP_VERSION` 为唯一版本真源，随 `/api/state` 暴露；状态栏右下角**常显**当前版本（如 `v0.4.3`）。
- **旧实例复用必须比对版本**：已有同端口服务存活时，仅当其版本与本包一致才复用；
  版本不一致（旧实例残留）则绕开换端口另起，防止「双击 bat 还是老版本」。

**FR-52 原生目录选择器（现代版）**（新增，重构 FR-39 的选择器实现）
- 「浏览」弹出的必须是 **Vista 风格现代通用对话框**（`IFileOpenDialog` + `FOS_PICKFOLDERS`）：
  有地址栏、「新建文件夹」按钮、大图标视图；禁止退回老式树形 SHBrowse 对话框
  （后者仅作 COM 不可用时的兜底）。
- 用户取消返回 `{canceled: true}`，前端静默处理不报错。

**FR-62 设置菜单收拢到齿轮（2026-10-10 三轮）**
- 齿轮（右上角）点开下拉，收拢全部设置类动作，**每项都有真实内容，不允许空壳**：
  翻译提示词… / 回到配置翻译服务 / 校验注入工具 / 运行日志 / 明暗模式 / 重置流程，底注显示当前版本号。
- 「校验注入工具」与「运行日志」是**只读 GET 端点**（`/api/kit/check`、`/api/logs`），不写盘：
  校验返回「工具齐备 · 共 N 项」或「缺 N 项：…」；日志返回版本/游戏目录/引擎/工具状态/词典条数与损坏字符/外部改动/流程位置 + 各步真实副标题。

**FR-63 导航双闸门与提取前置（2026-10-10 三轮）**
- **事故**：`max_step` 只是持久化数字，恢复时不校验目录/引擎是否还在 → 能从第 1 步一路点到第 4 步，
  第 2 步引擎识别形同虚设；且「没选游戏目录也照扫一遍」，报「提取完成 · 新增 0 条」+ 空表。
- **数字闸 + 事实闸两道**（`core/store.py:prereq_ok` + `nav`）：
  1 步需已选目录 · 2 步需目录 · 3/4 步需目录 **且**已识别引擎 · 5 步需词典有条目 · 6 步需已应用。
- 被拦时 `/api/nav` 返回 400 + `blocked_reason`（**具体缺哪一步**，不写笼统的「还没解锁」）；前端状态栏如实显示。
- **恢复流程也过事实闸**：目录失效 → 视作从未选过游戏（目录/引擎/位置全归零）；目录还在 → 引擎一并回认（`_ensure_engine` 单源），再从高往低找第一个前置成立的步骤。
- **提取前置早退**：无目录/目录已失效 → 返回 `{ok:false, error:"no_game"}` 并给可操作提示，**绝不**写 `extract.status=done` 或报「新增 0 条」。
- 选目录后自动回认引擎（与 `/api/detect`、`_restore_flow` 共用 `_ensure_engine` 单源），避免用户被无谓挡在第 2 步外。
- 提取内部已识别引擎时回写 `store.engine`（幂等，不覆盖用户手动选择），保证第 5 步管线类型正确。
