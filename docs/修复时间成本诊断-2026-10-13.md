# 修复时间成本诊断 · 2026-10-13

> 老板提问：「每次修复问题后花费的时间都超长，时间成本严重超支」。
> 本文全部结论来自本次实测与仓库历史，不读码推测。

---

## 〇、结论先行

**机器时间不是瓶颈（全套回归 55 秒）。时间成本的绝大部分花在「返工轮次」，
而返工的燃料是「假绿验证」——测试全绿但功能没生效，直到老板亲手试才发现。**

| 项 | 实测值 | 是否为瓶颈 |
|---|---|---|
| 单元 pytest（130 用例） | 16.3 s | 否 |
| 真浏览器冒烟（91 断言） | 34.3 s（其中 25.4 s 是硬 sleep） | 否 |
| 全套（单测+冒烟+端到端） | **54.7 s** | 否 |
| **FR-84 走的轮次** | **2 轮**（v0.6.2 填充 → v0.6.3 撤销） | **是** |
| **FR-85 走的轮次** | **3 轮**（v0.6.4 实现 → v0.6.7 返修 → 锁本身返工） | **是** |
| v0.6.2~v0.6.7 返工率 | **6 个版本里 2 个 FR 走了多轮 ≈ 40%** | **是** |

一次返工 = 重新定位 + 改代码 + 改断言 + 同步 5~7 份文档 + 跑三套验证 + 补回归测试。
从提交史看，10-11 当天 10 次提交，平均 1~2 小时一轮。**省时间的唯一杠杆是砍轮次。**

---

## 一、根因 1：判据验「代码写了什么」，不验「用户看到什么」→ 假绿

### 证据
- 冒烟共 **91 条断言**，只有 **24 条**用 `getComputedStyle()` 验真实渲染，
  其余 **67 条**验的是 class 属性、`STATE` 内部变量、DOM 文本等**代理指标**。
- v0.6.4 的 FR-85 事故是教科书案例：HTML 写隐藏**类** `class="… hidden"`、
  JS 翻隐藏**属性** `.hidden`，两套机制混用 → **按钮从头到尾没显示过**，
  而冒烟读 `.hidden` 属性判断可见性 → **86/86 全绿**。
  跨 3 个版本、2 天后由老板截图复报才暴露。
- 同类脆弱判据**至今仍在**，共 4 处（`tools/smoke_ui.js`）：

| 行号 | 断言 | 脆弱点 |
|---|---|---|
| 60 | `cfgModel` 可见性 | `classList.contains('hidden')` |
| 270/276 | `replModal` 开/关 | `classList.contains('hidden')` |
| 447 | 卡片首子元素 | `classList.contains('card-h')` |
| 534/544 | 行展开态 | `classList.contains('expanded')` |

这 4 处与 FR-85 事故同款：只要实现改用另一套机制，断言照样绿。

### 方案（强制判据分层）
1. **可见性 / 布局 / 字体**类断言：判据必须是 `getComputedStyle().display`
   或 `getBoundingClientRect()`，**禁止**用 class / 属性 / STATE 代理。
2. **文本 / 数值**类断言：必须取渲染后的 `innerText`，不取 `STATE` 字段。
3. 上表 4 处限期改完；改完在本文勾选。
4. 写进 `AGENTS.md` 门禁：新增断言若为「可见性/布局/字体」而判据是 class/属性 → 不许合入。

## 二、根因 2：新写的「回归锁」自己不验红 → 锁是假的

### 证据
`src/tests/test_review_2026_10_13.py` docstring 自述：
> v0.6.7 首版锁就栽在这：sed 伪造的双 class 标签骗过了正则，反向验证时 4 项全绿 = **假绿锁**。

即「为了防止假绿而写的锁，本身也是假绿的」。这直接多烧一轮。

### 方案
- **每个新增回归断言必须反向验红一次**：先把实现改回 bug 形态 → 断言必须 FAIL →
  再改回来 → 必须 PASS。两态都验过才算锁成立。
- 反向验红结果写进该测试文件的 docstring（谁验的、验的哪种 bug 形态）。
- 门禁：新回归测试若无「反向验红」记录 → 不许合入。

## 三、根因 3：方向性返工 —— 改之前没定验收形态

### 证据
FR-84 走了两轮：v0.6.2 按「左栏太空 → 填内容」实现 17 段说明，
老板复看否决「很臃肿」→ v0.6.3 全部撤销改成左对齐拉通。**一天内反转**。
`MEMORY.md` 已记教训：「面对空白反馈先问清要密度还是留白」——但没落到流程上。

### 方案
UI 类反馈改前先做**最小验收确认**，二选一即可，不要长篇：
- 出改前/改后同屏对比图（一次截图，10 秒）；或
- 一句话确认：「这块你要的是**加密度**还是**留白**？」

老板点头再写代码。方向对了，实现再糙也只改一次。

## 四、根因 4：环境摩擦 + 文档手工同步税

### 证据（本次逐条实测踩到）
| 摩擦 | 现象 |
|---|---|
| 入口路径 | `main.py` 在 `src/` 下；《本地测试指南》写 `python main.py`（从根跑必失败） |
| 测试路径 | 文档写 `pytest tests/`（实际 `src/tests/`） |
| import | pytest 必须带 `PYTHONPATH=src`，否则 4 个模块 `No module named 'gpot'` |
| 端口分裂 | 冒烟读 `GPOT_PORT`（默认 8731），端到端**硬编码 18771** → 跑全套要起两个服务 |
| node 依赖 | 必须手动设 `NODE_PATH=...\workspace\node_modules`，否则 playwright-core 找不到 |
| 本地 LLM | 不注入 `ST_NO_LOCAL_LLM=1` 会真跑 Ollama 占显存 |
| 文档 | 14 份 / 4461 行，每次改动同步 5~7 份；测试计数需手数 PASS 行（手写必漂） |

### 方案（已落地第一条）
✅ **`tools/verify.py` 已交付**——一条命令，自动注入全部环境变量、
自动起/收服务、统一端口 18771（端到端硬编码值，故只起一次）。

**2026-10-13 晚升级：默认自动判档**（老板亲定「按最小时间成本改」）：

```
python tools/verify.py            # 自动判档：T1 1.7s / T2 ≈50s / T3 ≈56s
python tools/verify.py --tier 3   # 强制全套（提交前）
python tools/verify.py --only unit  # 手动覆盖（调试）
```

判档由 `tools/tier.py` 按改动路径自动做（T1 文档 / T2 UI·测试 / T3 core·api·入口），
规则检查先跑、失败即止。改一行文档不再白等 50 秒（实测 T1 = 1.7s）。

剩余两条：
- 《本地测试指南》第 49~52 / 98 行路径订正为 `src/main.py` / `src/tests/`。
- 文档里的版本号、测试计数改为脚本回填（单一真源 `APP_VERSION` + pytest/冒烟输出取数），
  彻底消灭「手写必漂」。

## 五、根因 5：缺陷潜伏期长 —— 测试没覆盖真实交互路径

### 证据
FR-85 从 v0.6.4（10-11 20:12）到 v0.6.7（10-13）才暴露。**横跨 3 个版本**。
期间冒烟每次都全绿，说明 91 条断言里没有一条真正走完
「工具全就位 → 点击主按钮 → 进入下一步」这条用户路径。

### 方案
- 每个 FR 至少一条**路径级断言**（走完整交互），而不是只验元素属性。
- 优先补：第 2 步全就位 → 点主按钮 → 落第 3 步；这条就是 FR-85 漏掉的路径。

## 六、落地优先级

| 优先级 | 动作 | 成本 | 预期省时 |
|---|---|---|---|
| P0 | 判据分层强制（根因 1）+ 现存 4 处脆弱判据改造 | 中 | 砍掉「假绿→老板复报→整轮返工」，单条 FR 省 1~2 轮 |
| P0 | 新回归锁必须反向验红（根因 2） | 低 | 避免「锁本身返工」 |
| P1 | ✅ `tools/verify.py`（根因 4） | 已完成 | 每轮省 3~5 分钟拼命令 + 消除踩坑 |
| P1 | UI 改动前先确认验收形态（根因 3） | 极低 | 避免方向性反转（一次省一整轮） |
| P2 | 文档计数/版本脚本回填（根因 4） | 中 | 每轮省 10~15 分钟同步 |
| P2 | 补路径级断言（根因 5） | 中 | 缩短缺陷潜伏期 |

---

## 七、一句话总结

**不是跑得慢，是白跑。**
55 秒能跑完全套回归，但 67/91 的断言在验「代码写了什么」而不是「用户看到什么」，
所以全绿也挡不住 bug 上线，最后靠老板手测打回——这才是时间黑洞。
把判据改成验渲染结果 + 新锁必须反向验红，返工轮次砍掉，时间自然回来。
