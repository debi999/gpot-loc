## 一、结论摘要

| 维度 | 评价 |
|---|---|
| 架构分层 | **优秀**。core / api / ui 三层边界清晰，业务逻辑确实沉在 core，api 只做 HTTP 映射 |
| 注释与文档 | **优秀**。注释密度高且信息量大，记录了事故根因与实测数据，远超一般水平 |
| 测试 | **良好**。86 项全绿，端到端 13/13，但存在**测试资产名不副实**（承诺的 615 项回归实际不存在） |
| 健壮性 | **中等偏弱**。HTTP 层缺统一异常边界，3 处整数解析裸奔；翻译任务存在**取消后状态被踩**的并发缺陷 |
| 数据安全 | **需关注**。翻译结果不落盘、`sink/apply` 无前置闸会往 CWD 写文件 |

**核心判断**：这是一份**架构纪律执行得很到位、但边界防御薄如纸**的代码。分层/单源做得比多数生产项目好，但所有外部输入（HTTP query/body、CORS、静态文件路径）几乎裸奔进入业务层。测试覆盖的是"正常路径 + 精心构造的边界"，缺的是"畸形输入 + 时序竞争"。

**共发现 14 个问题**：P0 × 1、P1 × 4、P2 × 5、P3 × 4。

## 二、P0 —— 数据丢失级

### P0-1 翻译任务跑完，译文永不落盘（除非用户手动走"保存并应用"）

**位置**：`src/gpot/core/translate.py:96-186`（worker 函数）/ `src/gpot/api/server.py:730-741`

**现象**：翻译任务完成后，`tstore.entries` 里译文已就绪、`tstore.dirty = True`，但**没有任何一处调用 `tstore.save()`**。

```
$ python -c "跑一个翻译任务"
job done= 1
entry translation = '你好'      ← 内存里有
tstore.dirty      = True
tstore.path       = None       ← 连 path 都没设
磁盘上有文件吗    = False       ← 磁盘上没有
```

**影响链**：
1. 用户在第 4 步点"开始翻译"，等进度条 100%，第 6 步副标题刷新但词典文件始终不存在。
2. `TranslationStore.path` 在翻译路径上从未被赋值——只有 `/api/game` 和 `extract()` 会设。所以翻译过程中即使手动调 `save()` 也会写错位置。
3. `tstore.dirty` 全仓**只被写、从不被读**（`grep -rn "\.dirty"` 确认：生产代码零读取点，仅两处测试断言 `dirty` 为 True）。它是一个纯粹的死标志——本该是"该不该落盘"的判据，却没人用。
4. 用户若此时重启程序，全部译文蒸发。

**为什么这是 P0**：用户主观认知是"翻译完成 = 资产已保住"。程序给的是 100% 进度 + 绿色完成态，磁盘上却什么都没有。这是**静默的资产丢失**，且不会有任何报错。

**修复建议**（遵循 AGENTS.md 铁律④，逻辑下沉 core，api 只映射）：

```python
# core/translate.py —— worker 收尾处
with store.lock:
    ...
    if job["done"]:
        try:
            if not tstore.path:
                gdir = (store.game or {}).get("path") or ""
                if gdir:
                    tstore.path = kernel.translation_file_path(gdir)
            if tstore.path:
                tstore.save()          # 原子写 + .bak 三代轮转
        except Exception as e:
            job["result"] = "finished_but_save_failed"
            store.translate["save_error"] = str(e)[:200]   # 诚实性 NFR-9：不静默吞
```

同时建议让 `dirty` 真正发挥作用：`_STATE.to_dict()` 暴露 `tstore_dirty`，前端在离开第 4 步时若有未落盘改动则弹提示。

## 三、P1 —— 功能正确性

### P1-1 取消的任务会踩掉新任务的 `running` 标志（并发时序缺陷）

**位置**：`src/gpot/core/translate.py:110-118`（`cancel_job`）+ `175-186`（worker 收尾）

**复现**（构造真实时序，实测输出）：

```
t=0.2  running flag = True   (job2 正在跑)
t=2.2  running flag = False  ← job1 的收尾把 job2 的标志踩了
3rd job accepted while job2 still running?  True   ← 第三个任务被放行
job1 done 0   job2 done 80   job3 done 80        ← job2 和 job3 同时在写同一批条目
```

**根因**：`cancel_job` 立刻把 `store.translate["running"] = False`，而 job1 的 worker 线程还在跑（`run_chunk` 里 `time.sleep` 不可中断）。等 job1 走到收尾的 `with store.lock:` 块时，**无条件**写 `store.translate["running"] = False`——此时这个标志已经属于 job2 了。

**后果**：
- 同一批 80 条被两个任务同时翻译（ThreadPoolExecutor 并发写同一批 entry），指标虚高。
- 前端"已有翻译任务在进行"（409）这道闸完全失效。
- `job["progress"]` 与 `store.translate` 指标互相污染。

**修复建议**：worker 收尾时校验任务身份，只清理自己的状态：

```python
with store.lock:
    job["running"] = False
    ...
    if store.jobs.get(job["id"]) is job:      # 身份校验：这是我的标志我才清
        store.translate["running"] = False
    # 或更稳妥：维护 job id 白名单
    store.translate["active_jobs"] = {j for j, x in store.jobs.items() if x["running"]}
    store.translate["running"] = bool(store.translate["active_jobs"])
```

### P1-3 `/api/sink/apply` 无前置闸，未选游戏目录时往 CWD 写文件

**位置**：`src/gpot/core/sink.py:146-154` + `src/gpot/api/server.py:798-806`

```python
if kind == "runtime":
    dest = (kit_catalog.sink_path(eng, gdir) if eng and gdir else None) \
        or kernel.translation_file_path(gdir)      # ← gdir 为空时 os.path.join('') → 相对路径

```

实测（干净状态、无游戏目录）：
```

cwd 下实际落盘: ['BepInEx\Translation\zh\Text\_AutoGeneratedTranslations.txt']

**问题**：`translation_file_path('')` 里 `os.path.join('', 'BepInEx', ...)` 返回**相对路径**，于是词典被写进**进程当前工作目录**——可能是一个完全无关的目录（我测试时就污染了 Temp）。

注意 `/api/restore` 和 `/api/open-dir` 都有前置闸并返回 400，唯独 `sink/apply` 这条**真正写盘的**路径没有。同一分支的 `none` 形态（`sink.py:172`）同样用 `gdir or os.getcwd()`。

    raise RuntimeError("还没选游戏目录 —— 先回第 1 步选对目录再保存")
```

### P1-4 HTTP 层缺统一异常边界，3 处整数解析裸奔

**位置**：`src/gpot/api/server.py:591`（`_rows`）、`:703`（`/api/nav`）

```python
limit  = min(5000, max(1, int(q.get("limit", ["5000"])[0])))   # 无 try
offset = max(0, int(q.get("offset", ["0"])[0]))                # 无 try
step   = int(b.get("step", 0))                                  # 无 try
```

实测（打真实 HTTP 端点）：
```
GET  /api/rows?limit=abc  -> RemoteDisconnected（连接被断开，无响应）
GET  /api/rows?offset=x  -> RemoteDisconnected
POST /api/nav step=abc   -> RemoteDisconnected
```

`BaseHTTPRequestHandler` 没有 `try/except` 包裹 `do_GET/do_POST`，异常直接冒泡 → 线程崩 → 客户端拿到"连接被关闭"而非 400。这违反项目自己的诚实性原则（NFR-9"如实告知"）——前端只能看到"网络错误"，无法区分"参数写错"和"后端挂了"。

**修复建议**：要么给 `_Handler` 加一层薄薄的兜底（`except ValueError → 400 {"error":"bad_param"}`，`except Exception → 500 {"error":"internal"}` 并落日志），要么用小工具函数单源化 int 解析。后者更符合铁律④。

### P2-1 `check_assets.py` 与 `kernel.py` 双份 `normalize` / `translation_file_path`，且**已经漂移**

**位置**：`src/gpot/api/server.py:700-708`

### P2-4 前端 `innerHTML` 未统一转义，`esc()` 覆盖不全

**位置**：`src/gpot/ui/assets/app.js:1394, 1396, 766, 511-514, 1495` 等

表格数据走了 `esc()`（`:830`），但以下位置直接拼 `innerHTML`：

## 六、做得好的地方

审查不是只挑毛病——以下几处值得明确表扬：

1. **分层纪律是真的**。`store.replace_rows` / `dedup_rows` / `edit_row` / `recent_games`、`detection.find_game_exe`、`winframe.hit_test` 全部从 api 下沉到 core，且都有单测。api 层确实只剩 HTTP 映射与错误码转换。

2. **单源化有真实成果**。`translate.SMAP` 一张表同时服务 `_rows` 筛选与 `select_targets`，注释还写明了历史教训「状态筛选键没过映射表 → 永远 0 命中」。`providers._model_ids` 把 `fetch_models` 与 `test_connection` 的重复解析合并。

3. **写盘原子性做得专业**。`TranslationStore.save` 用 临时文件 + `fsync` + `os.replace`，备份轮转顺序正确（先备份完整版本再替换），失败时清理 `.part`/`.tmp` 且保留主文件。`kit_installer._write_atomic` 同一套策略。

4. **注释记录了事故而非流水账**。`kit_installer._safe_join` 防 zip 目录穿越、`_norm_show` 解释为什么"先 replace 再 normpath"、`extract._collect` 用包装 `kernel` 模块属性来统计护栏计数而不改旧逻辑——这些都体现了"为什么这样写"的思考。

5. **`kit_installer` 的默认不覆盖原则**。`_should_write` 默认 skip 已有文件，保护用户调好的 `BepInEx.cfg`；`_cache_is_good` 在无 sha256 时降级为体积校验并**明说**"校验强度弱"，不假装做到内容级校验。

6. **诚实性原则贯彻得好**。`_kit_tools` 删掉恒空的假列 `version`（而不是留一排"—"）、`prereq_msg` 专门为被拦步骤准备人话、`rpgmaker_engine.apply` 改写 RPGM 数据前强制全量备份 + 一键还原。
